Archive message ranges with intelligent summaries for context management.

**TWO-PHASE COMPACTION FLOW**

IMPORTANT: Message IDs are NOT visible by default. You cannot see [msg_xxx] prefixes on messages during normal conversation. The two-phase flow enables ID visibility:

**Phase 1 - Prepare Mode (enable ID visibility):**
Call compact with NO ranges to enable message ID visibility:
```json
{ "ranges": [] }
```
This enables ID prefixes on all messages so you can see them in the next response.

**Phase 2 - Execute Mode (perform actual compaction):**
After seeing the message IDs, call compact with specific ranges:
```json
{
  "ranges": [
    { "startMessageId": "msg_xxx", "endMessageId": "msg_yyy" }
  ]
}
```

CRITICAL: Do NOT generate or guess message IDs. Only use IDs you can actually see prefixed on messages AFTER calling prepare mode. If you reference IDs that don't exist, the compaction will fail.

This tool compacts message ranges by:
1. Generating a concise summary (1-3 sentences) of the content
2. Extracting 3-7 semantic index terms for future retrieval
3. Storing archive metadata on messages
4. Replacing original content with a [SMART_ARCHIVED] placeholder in context

WHEN TO USE:

**User-Directed Compaction:**
Use when the user explicitly requests archiving/compacting messages:
- "archive the authentication discussion"
- "compact messages msg_abc to msg_xyz"
- "save our earlier debugging session"
- "free up context space"
- "compact everything before this"

**AUTONOMOUS COMPACTION DECISION:**
You can proactively decide to compact WITHOUT user request. Monitor the context gauge checkpoints that appear in conversation (format: [CONTEXT GAUGE: X / Y tokens (Z%)]).

**PROACTIVE COMPACTION TRIGGERS (any gauge level):**
Compact IMMEDIATELY when you detect these patterns, regardless of context percentage:

1. **Completed task blocks:** When a unit of work is DONE, compact it:
   - Bug investigation concluded and fix applied
   - Plan written and approved
   - Code review finished
   - Feature implemented and tested
   - Research/exploration completed with findings captured
   - Any task where you've moved on to something different

2. **Project/repo switches:** When conversation shifts to a different codebase or project:
   - Archive the previous project's context before diving into the new one
   - The old context is unlikely to be relevant and will clutter working memory

3. **Multiple context gauges seen without compaction:** If you've seen 2+ context gauges in a session and haven't compacted, you're being too conservative. Review completed work and archive it.

**Do not wait for high context utilization to compact completed work.** A 25% context with finished debugging sessions should be compacted. Keeping stale completed work wastes context space that could be used for the current task.

**When to autonomously compact (gauge-based triggers):**

1. **Any gauge level** with completed work:
   - Compact finished task blocks immediately (see triggers above)
   - Don't let completed work accumulate waiting for a threshold

2. **Context gauge >50% utilization:**
   - Actively look for compaction opportunities
   - Large tool outputs whose insights are captured should be archived
   - Completed discussions should not remain in raw form

3. **Context gauge >80% utilization:**
   - Strongly consider compacting
   - Prioritize content where learnings are already captured elsewhere
   - Multiple ranges may be appropriate to maximize space

**Content detection patterns:**
- Voluminous tool outputs: File reads, grep results, command outputs - IF key insights are captured in your responses/thinking
- Completed discussions: Feature discussions that concluded, debugging resolved, decisions made and documented
- Reference material: Documentation/examples consulted where relevant information is now in working context

**CRITICAL: Before compacting, verify the learnings are preserved**
Raw content can be archived when the *meaning* is captured elsewhere:
- In your prior responses/analysis (e.g., "learned X works this way")
- In the compaction summary you'll generate
- In code/artifacts created as a result
- In decisions/conclusions already documented

Do NOT compact just because you "read" something - compact when the insights are safe.

**Context gauge interpretation:**
- <30%: Compact completed work; no need to compact ongoing work
- 30-50%: Compact completed work; monitor ongoing discussions
- 50-80%: Actively look for compaction opportunities; completed work should already be archived
- >80%: Strongly consider compacting; prioritize freeing significant space

**LOOP/ITERATION DETECTION:**
When working through debugging, retrying, or iterating:

1. **Detect iteration patterns:** Recognize when you're in a loop (debugging attempts, retry cycles, trial-and-error fixing)

2. **When to compact iterations:** Prior iterations may be compacted once a NEW iteration begins and you have learned from the previous ones

3. **CRITICAL - Before compacting loop iterations, identify what MUST be preserved:**
   - What was tried in each iteration
   - What was learned (errors, insights, partial successes)
   - Any constraints discovered that affect future attempts
   - The current hypothesis or next approach

4. **The summary MUST capture learnings, not just "tried X, failed"**

**Good iteration summary example:**
"Iterations 1-3: Tried fixing auth via token refresh (failed - tokens were valid), session storage (failed - sessions persisting correctly), found root cause in middleware ordering. Constraint: must apply auth middleware before rate limiting."

**Bad iteration summary example:**
"Debugging session for authentication issues."

The bad example loses critical information about what was tried and learned. A future retrieve would not restore the debugging insights.

**RANGE PARTITIONING:**
Consider splitting a contiguous range into MULTIPLE archives when:

1. **Different topics/tasks intermixed:** A single discussion covered multiple unrelated topics
   - Separate summaries are more useful for targeted retrieval later
   - Example: Messages 1-20 covered auth setup (1-8), database schema (9-15), and deployment (16-20) → partition into 3 ranges

2. **User might want partial retrieval:** Different sections have different relevance
   - Example: A code review covered 5 files; partition so user can retrieve comments on specific files

3. **Single summary would lose distinctions:** Important nuances between sub-topics
   - Example: Two competing approaches were discussed; each deserves its own summary capturing trade-offs

**How to identify topic boundaries:**
- Look for context switches (new file, new problem, new feature)
- Observe when the discussion focus shifts
- Note when you started working on something different

**Partitioning in practice:**
Provide multiple ranges in a SINGLE compact call (not multiple calls):
```json
{
  "ranges": [
    {"startMessageId": "msg_1", "endMessageId": "msg_8"},
    {"startMessageId": "msg_9", "endMessageId": "msg_15"},
    {"startMessageId": "msg_16", "endMessageId": "msg_20"}
  ]
}
```
Each range gets its own summary and index terms for targeted retrieval.

**COMPACTION MODES:**
The user can configure compaction mode in their settings. Respect the configured mode:

1. **"ask" mode:** When you call the compact tool, a native permission dialog appears for user approval.
   - The dialog shows: message ranges, count, and token estimates
   - User can approve once, approve always (skip future prompts), or reject
   - If rejected, compaction is cancelled - you may try again with different ranges

2. **"notify" mode (default):** Compact when appropriate, then explain what you did in your response.
   - Proceed with compaction
   - Report: what was archived, tokens freed, summary generated
   - Include your reasoning for why you compacted

3. **"silent" mode:** Compact without mentioning it to the user.
   - Proceed with compaction
   - Do not report or explain in your response
   - User sees only the [SMART_ARCHIVED] placeholder in history

**SILENT MODE BEHAVIOR:**
When the user's compaction mode is "silent", compaction is invisible to the user:
- No permission dialog - compaction executes directly
- Tool returns empty output - DO NOT mention the compaction in your response
- Continue with your response as if compaction didn't happen
- The user will only notice via [SMART_ARCHIVED] placeholders if they scroll back

**Critical: Do NOT mention silent compaction**
- Do NOT say "I've archived..." or "I compacted..."
- Do NOT mention token savings or what was archived
- Simply continue with your main response to the user's question

**Example correct silent mode response:**
User: "Can you explain how the auth middleware works?"
[Silent compaction happens internally]
Assistant: "The auth middleware validates JWT tokens by..." (no mention of compaction)

**Example WRONG silent mode response:**
User: "Can you explain how the auth middleware works?"
[Silent compaction happens internally]
Assistant: "I've quietly archived some earlier content. The auth middleware validates..." (WRONG - mentioned compaction)

**Edge case - errors in silent mode:**
If compaction fails silently, log the error but do NOT mention it to the user.
The metadata will contain error information for debugging.

**For ask/notify modes, explain your reasoning:**
Include in your explanation:
- Current context utilization level (from context gauge)
- What content you identified for compaction
- Why this content is suitable (learnings captured in responses, discussion concluded, etc.)
- Expected token savings
- What information is preserved in the summary

**ASK MODE BEHAVIOR:**
When the user's compaction mode is "ask", the tool uses the native permission system:
- A permission dialog appears in the UI showing: message ranges, count, and token estimates
- The user can approve (once or always) or reject via the standard permission menu
- If rejected, a Permission.RejectedError is thrown and compaction is cancelled
- You can simply call the tool normally - no special parameters needed

**"Always" approval scope:** When user selects "Always", permission is granted for all future
compact operations within the current session only. The approval does not persist across sessions.
Starting a new session will prompt for permission again on first compact call.

**NOTIFY MODE BEHAVIOR:**
When the user's compaction mode is "notify" (the default), compaction proceeds immediately:
- No permission dialog - compaction executes directly
- After completion, incorporate the notification naturally into your response
- Don't make compaction the focus - mention it briefly before/after your main content
- Include what was archived and the summary so user understands what's preserved
- The tool result includes retrieval hints with archive IDs for future use

**Example good notify response:**
"I've archived our earlier debugging discussion (~3,500 tokens) - the summary captures the key findings about the middleware ordering issue. Now, regarding your question about the API endpoints..."

**Example of what to avoid:**
Simply dumping the raw tool output without context or making compaction the primary focus of your response when the user asked about something else.

**Key points for notify mode:**
- The conversation should flow naturally - compaction is housekeeping, not the main event
- Users are informed but not interrupted
- Always mention how to retrieve if needed (the tool provides archive IDs)
- Do NOT ask the user to confirm or respond to the compaction notification - continue with your main response immediately

HOW TO IDENTIFY MESSAGE RANGES:
1. **Direct IDs**: User provides specific message IDs (e.g., "compact msg_abc to msg_xyz")
2. **Topic-based**: Identify messages discussing the topic user mentions, determine first and last message IDs in that discussion
3. **Positional**: "before this" means messages prior to current exchange; "first half" means early messages

Note: "msg_abc" is a placeholder. Actual message IDs follow the format `msg_[HEX_TIMESTAMP][RANDOM_BASE62]`
(e.g., `msg_019512a8bc34XyZ9AbCdEf`). See `packages/opencode/src/id/id.ts` for the full ID generation logic.

PARAMETERS:
{
  "ranges": [{                          // Optional: omit or pass empty array for prepare mode
    "startMessageId": "msg_abc",        // Required within range: first message ID
    "endMessageId": "msg_xyz"           // Optional: last message ID (defaults to start for single message)
  }]
}

**Prepare Mode (Phase 1):** Omit ranges or pass empty array `[]` to enable message ID visibility.
**Execute Mode (Phase 2):** Pass one or more ranges to perform actual compaction.

Multiple ranges can be archived in a single call.

VALIDATION RULES:
- All message IDs must exist in the session
- startMessageId must come before endMessageId chronologically
- Start and end messages must not already be archived
- Multiple ranges must not overlap

AFTER COMPACTION - REPORT TO USER:
- Confirmation: "Archived X messages from msg_abc to msg_xyz"
- Token savings: "Freed ~Y tokens of context space"
- Summary: Show the generated summary so user knows what's preserved
- Retrieval hint: "Use the retrieve tool with the archive ID to restore archived content if needed"

**Example autonomous compaction explanation:**
"Context is at 72%. The earlier file exploration (~4000 tokens) yielded insights I've already captured in my analysis above (channels are simplex, auth requires two-phase handshake). The summary will preserve these key findings, so the raw file contents can be archived."

The archived messages will appear as a [SMART_ARCHIVED] placeholder in conversation history, showing the summary and index terms.
